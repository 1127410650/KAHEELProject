# ربط مشاريع گحيل مستقبلًا

## الوضع الحالي

«گحيل» يعلن هوية تكامل ثابتة في:

`/.well-known/kaheel-project.json`

هذه طبقة اكتشاف فقط. لا تنشئ اتصالًا، ولا تمنح صلاحية، ولا تشارك بيانات أو أسرارًا.

## القاعدة المعمارية

كل مشروع جديد يبقى منتجًا مستقلًا بمستودعه وقاعدة بياناته ونشره. الربط مع «گحيل»
يكون ثنائي الاتجاه بواسطة مراجع خارجية مبهمة، وليس بواسطة مشاركة الجداول أو مفاتيح
`service_role` أو نسخ المستخدمين والسجلات.

- لا توجد مفاتيح أجنبية بين قاعدتي بيانات منفصلتين.
- لا يكفي تطابق البريد أو الجوال أو الهوية أو السجل التجاري لمنح وصول.
- الربط لا يرث أي دور أو صلاحية من مشروع إلى آخر.
- كل نطاق مشاركة يحتاج موافقة صريحة ويمكن إلغاؤه مع أثر تدقيقي.
- لا يقرأ أي مشروع إلا البيانات التي يعيدها له المشروع الآخر عبر واجهة خادمية محددة.
- الحساب والكيان والمشروع والعضو تظل معزولة في مصدرها الأصلي.

## التسلسل المعتمد عند وجود المشروع الثاني

1. يقرأ كل مشروع مستند الاكتشاف العام للمشروع الآخر ويتحقق من البروتوكول والهوية.
2. يبدأ المستخدم الربط من الحساب أو الكيان الذي يملكه فعلًا.
3. يصدر الخادم رمزًا أحادي الاستخدام، قصير العمر، ومقيدًا بالمشروع والنطاقات المطلوبة.
4. يؤكد الخادم المقابل الرمز ويعيد مرجعًا خارجيًا مبهمًا؛ لا يعيد معرفات الجداول المحلية.
5. تُحفظ العلاقة بحالة `pending` ثم `active` بعد الموافقة الصريحة من الطرفين.
6. كل طلب لاحق يحمل نطاقًا محددًا ويُراجع خادميًا؛ الواجهة لا تمنح الوصول.
7. الإلغاء يوقف التبادل فورًا ويُبقي سجل التدقيق دون حذف تاريخ الأعمال.

## ما لم يُنشأ الآن عمدًا

لم تُنشأ جداول تكامل تخمينية داخل قاعدة الإنتاج، لأن المشروع الثاني وعقوده ونطاقاته غير
موجودة بعد. عند وجوده، تُضاف مهاجرة واحدة مراجعة إلى مخطط خاص غير معروض للـData API،
ثم تُبنى واجهات الربط الخادمية مع RLS/المنح المناسبة واختبارات العزل. هذا يمنع جداول
مكررة أو عقدًا خاطئًا يصعب ترحيله لاحقًا.
