أريد تنفيذ مرحلة ثالثة مستقلة ومكملة باسم **«الإغلاق الشامل والتكامل التشغيلي لمنصة كحيل»**.

هذه المرحلة لا تعيد بناء ما تم في المرحلتين السابقتين، ولا تنشئ لوحة ثالثة، ولا تنسخ نظام المحتوى أو التحليلات أو الصلاحيات. المطلوب مراجعة المنصة كلها كمنظومة واحدة، سد الفجوات المتبقية، وربط الوحدات بحيث تصبح كحيل قابلة للتشغيل بمستوى منصة كبيرة ومتكاملة.

المقصود بمستوى عالمي هو:

- كل وحدة مرتبطة ببياناتها وصلاحياتها وأحداثها وتنبيهاتها واختباراتها.
- كل عملية حساسة لها اعتماد وسجل وتراجع وخطة فشل.
- كل رقم له تعريف ومصدر ويمكن التحقق منه.
- كل Feature لها حالة تشغيل واضحة ومفتاح تفعيل وتعطيل آمن.
- كل خدمة حرجة لها مراقبة وهدف أداء ومسؤول وRunbook.
- لا توجد شاشة فارغة أو زر وهمي أو وحدة تبدو مكتملة وهي غير مرتبطة فعليًا.
- لا توجد بيانات مكررة أو وصول يعتمد على إخفاء الواجهة فقط.

## 1. ترتيب المراحل وعدم التكرار

اقرأ أولًا الأمرين السابقين وتقارير التدقيق الناتجة عنهما. نفذ هذه المرحلة داخل **مركز قيادة مدير المنصة العام** و**استوديو المحتوى والتحليلات** نفسهما.

قواعد ملزمة:

1. لا تنشئ Dashboard جديدة.
2. لا تنشئ نظام صلاحيات جديدًا.
3. لا تنشئ نظام Analytics أو Events ثانيًا.
4. لا تنشئ نظام حملات أو مواضع إعلانية ثانيًا.
5. لا تنشئ حسابًا أو هوية أو متجرًا أو إعلانًا أو منتجًا أو مشروعًا مكررًا.
6. أعد استخدام سجل العمليات وصندوق العمل والتنبيهات والهوية النشطة و`tenant_id` و`owner_user_id` والعلاقات الحالية بعد التحقق من الأسماء الفعلية.
7. إذا كانت المرحلة السابقة غير مكتملة أو تقريرها يحتوي Critical/Error غير مغلق، لا تبدأ ترحيلات هذه المرحلة. وثق الحاصر وأوقف التنفيذ عنده.
8. لا تنفذ Publish للمنصة، ولا تستخدم بيانات حقيقية.

## 2. بوابة الاكتمال الإلزامية لكل وحدة

أنشئ **Definition of Done موحدة**. لا تعتبر أي وحدة مكتملة حتى تحتوي على جميع البنود التالية أو تحمل حالة «غير منطبق» مع سبب موثق:

1. الهدف والمستخدم المستفيد.
2. مالك الوحدة والمسؤول التشغيلي عنها.
3. المسارات والشاشات الفعلية.
4. مصدر البيانات الرئيسي وعدم وجود نسخة مكررة.
5. حالات دورة العمل والانتقالات المسموحة.
6. الأدوار والصلاحيات الخادمية.
7. RLS/Grants/RPC/Functions اللازمة.
8. حالات Loading وEmpty وError وForbidden وOffline أو Degraded عند الحاجة.
9. سجل العمليات والأثر قبل/بعد للإجراءات الحساسة.
10. أحداث التتبع وتعريف المقاييس.
11. التنبيهات وقواعد التصعيد.
12. المهام المجدولة أو Queues وRetries إن وجدت.
13. حدود الأداء والتكلفة.
14. سياسة الاحتفاظ والحذف والأرشفة.
15. النسخ الاحتياطي والاستعادة أو سبب عدم الانطباق.
16. السلوك عند فشل الاعتماد الخارجي.
17. Feature Flag وKill switch عندما تكون الوحدة قابلة للإيقاف.
18. الاختبارات الآلية واليدوية.
19. توثيق التشغيل وRunbook.
20. دليل قابل للتحقق على نجاح الوحدة.

أي وحدة ينقصها بند ضروري تبقى **جزئية** ولا تسجل «مكتملة».

## 5. مراقبة أداء الصفحات والمكونات

أضف وحدة **Page & Component Performance** داخل مركز القيادة واستوديو المحتوى.

### أهداف Core Web Vitals

استخدم الأهداف الحالية كنقطة بداية قابلة للمراجعة:

- LCP لا يتجاوز 2.5 ثانية.
- INP لا يتجاوز 200ms.
- CLS لا يتجاوز 0.1.
- القياس الأساسي عند percentile 75 للجوال والكمبيوتر بصورة منفصلة.

اجمع بين:

- قياس Lab قبل النشر.
- Real User Monitoring بعد التشغيل.
- مقارنة النسخة الحالية بالنسخة السابقة.
- التقسيم حسب الصفحة والمقاس والدولة ونوع الاتصال بصورة مجمعة.

### Performance Budgets

أنشئ حدودًا قابلة للإدارة حسب نوع الصفحة:

- الحجم الإجمالي للصفحة.
- حجم JavaScript وCSS.
- عدد وحجم الصور.
- حجم الفيديو ونمط التحميل.
- عدد الخطوط وأوزانها.
- عدد طلبات الشبكة.
- عدد مكونات Carousel والفيديو والمحتوى الديناميكي.
- وقت استجابة API والاستعلامات الحرجة.

في Preflight داخل استوديو المحتوى:

- اعرض أثر المكون الجديد على الميزانية.
- امنع نشر خطأ حرج مثل أصل ضخم أو Layout shift واضح.
- اسمح بتجاوز Warning فقط لصلاحية أعلى وسبب مسجل.
- اقترح ضغط الصورة أو Lazy loading أو استبدال الأصل.
- لا تخفِ الفشل بإزالة القياس.

أضف Dashboard للصفحات الأبطأ، الانحدارات بعد النشر، وأثقل المكونات والأصول.

## 6. مركز الاعتمادية والمراقبة

أضف داخل مركز القيادة شاشة **صحة المنصة والاعتمادية**، تعتمد على مؤشرات فعلية لا Mock.

راقب لكل خدمة حرجة:

- Latency.
- Traffic.
- Errors.
- Saturation/Capacity.

الخدمات الأساسية تشمل:

- الدخول والجلسات.
- السوق والرئيسية.
- البحث.
- رفع الملفات.
- النشر والمحتوى.
- استقبال أحداث التحليلات.
- الرسائل وطلبات التواصل.
- الطلبات والمشاريع.
- Jobs والتقارير.
- الفواتير الإعلانية عند تفعيلها.

أنشئ SLI/SLO واقعية لكل خدمة بعد قياس Baseline. لا تستخدم أرقام توافر تجميلية. اعرض:

- الحالة الحالية.
- آخر فشل.
- مدة الفشل.
- نسبة النجاح.
- p50/p95/p99 عند الحاجة.
- المسؤول وRunbook.
- آخر إصدار أو تغيير مرتبط.

التنبيه يجب أن يكون قابلًا للإجراء ومنخفض الضوضاء. فرّق بين:

- P0 توقف واسع أو تسرب أمني.
- P1 فشل وظيفة حرجة لعدد كبير.
- P2 تدهور أو تأخر يحتاج معالجة.
- P3 ملاحظة تشغيلية غير عاجلة.

كل Incident يملك رقمًا وحالة وقائدًا وتسلسلًا زمنيًا وإجراءات تخفيف وسببًا جذريًا وPostmortem عند الإغلاق.

## 7. مفتاح الطوارئ والوضع الآمن

أنشئ **Safe Mode & Kill Switch Center** بصلاحيات شديدة الحساسية.

يعمل على مستويات منفصلة:

- المنصة كاملة.
- سوق/دولة محددة.
- وحدة محددة: البحث، التتبع، المحتوى الديناميكي، الحملات، التواصل، التجارة.
- صفحة أو Surface.
- حملة أو Placement.
- Edge Function أو Job محددة إذا كانت البنية تسمح.

قواعد الأمان:

- لا يعني Safe Mode إيقاف Auth أو فقد الوصول الإداري.
- لكل مفتاح Fallback واضح: آخر نسخة منشورة، صفحة صيانة، بحث أساسي، تعطيل استقبال حدث منخفض القيمة، إيقاف حملة، أو إخفاء زر غير متاح.
- التفعيل يحتاج سببًا ومدة متوقعة وتأثيرًا ظاهرًا.
- الإجراء العالمي أو استعادة قاعدة البيانات يحتاج موافقتين منفصلتين وعدم موافقة الشخص على طلبه.
- الإعداد يحمل Expiry اختياريًا حتى لا يبقى وضع الطوارئ منسيًا.
- سجل كامل قبل/بعد والمنفذ والموافق والوقت.
- اختبر Safe Mode دوريًا في بيئة آمنة.
- لا تستخدمه كبديل لإصلاح السبب الجذري.

## 8. الفحص الدوري لصحة المحتوى والروابط

أنشئ Jobs دورية آمنة تفحص:

- الروابط الداخلية والخارجية المسموحة.
- Redirect loops وChains الطويلة.
- صفحات بلا نسخة منشورة أو بلا محتوى أساسي.
- Blocks تشير إلى هدف موقوف.
- صور أو ملفات مفقودة.
- أصول مستخدمة بلا Alt.
- حملات منتهية ما زالت ظاهرة.
- Placements بلا بديل.
- بيانات ديناميكية تعيد صفرًا باستمرار.
- مكونات غير معروفة أو إصدار Schema قديم.
- أحداث Tracking لم تعد تصل من صفحة منشورة.
- Search index متأخر عن مصدر البيانات.
- سجلات يتيمة أو علاقات مكسورة.
- Jobs متوقفة أو تعيد المحاولة بلا نهاية.

استخدم Job registry موحدًا مع:

- تعريف Job وإصدارها.
- جدول تشغيل.
- Unique idempotency key.
- الحالة والمحاولات.
- Lock آمن بين Workers، واستخدام Queue pattern غير حاصر مثل `SKIP LOCKED` عند ملاءمته.
- Exponential backoff وحد أقصى للمحاولات.
- Dead-letter state.
- Last success/next run/duration/error summary.
- زر إعادة تشغيل لصلاحية محددة.
- سجل دون أسرار أو Payload حساس.

تحول النتائج إلى عناصر في صندوق عمل المدير حسب الخطورة، ولا ترسل عشرات التنبيهات المتكررة للمشكلة نفسها.

## 9. النسخ الاحتياطي والاستعادة واستمرارية العمل

ابنِ **Backup & Restore Governance** لا زر استعادة مباشر غير منضبط.

### نطاق النسخة

غطِّ:

- قاعدة البيانات ومخططها ومحتواها.
- ملفات Storage نفسها، وليس Metadata فقط.
- ملفات Migrations.
- Source الخاص بـEdge Functions.
- إعدادات Auth وProviders وRedirects.
- إعدادات Realtime وExtensions وWebhooks.
- إعدادات RLS/Functions/Triggers.
- CMS pages/versions/navigation/campaigns كنسخة تصدير مستقلة قابلة للفحص.
- Feature flags وRunbooks وقوالب التنبيهات.
- قائمة أسماء الأسرار المطلوبة، لا قيم الأسرار داخل ملف غير آمن.

### السياسة

- عرّف RPO وRTO لكل نوع بيانات.
- اربط الخطة بإمكانات الاشتراك الفعلية؛ لا تفترض PITR مجانيًا أو مفعلًا.
- إذا لم تتوفر نسخة آلية كافية، وثق Export دوريًا آمنًا.
- النسخ مشفرة ومقيدة الوصول ولها Retention واضحة.
- تحقق من Checksum واكتمال النسخة.
- افصل نسخة قاعدة البيانات عن نسخة ملفات Storage لأن استعادة DB لا تعيد الملفات المحذوفة تلقائيًا.
- امنع حفظ أسرار أو كلمات مرور داخل التقارير.

### اختبار الاستعادة

- اختبر الاستعادة إلى بيئة/فرع/مشروع آمن، لا فوق الإنتاج.
- تحقق من Auth وRLS وStorage وEdge Functions والمهام بعد الاستعادة.
- قارن عدد السجلات والعلاقات وعينات الملفات.
- وثق الزمن الفعلي للاستعادة وبيانات ما قد يُفقد.
- لا تعتبر النسخ الاحتياطي مكتملًا قبل نجاح Restore drill موثق.
- الاستعادة الإنتاجية إجراء مدمر يحتاج موافقتين وخطة توقف واتصال واضحة؛ لا تنفذها ضمن هذه المرحلة.

## 10. محرك البحث الموحد

طوّر البحث الحالي ليصبح **خدمة اكتشاف موحدة** داخل المنصة، من دون خلط البحث العام بالبحث الإداري الحساس.

### نطاق البحث العام

ابحث فقط في السجلات العامة المنشورة والمسموحة:

- الإعلانات.
- المتاجر/المنشآت العامة.
- المنتجات عند تفعيلها.
- التصنيفات والأنشطة.
- الفرص وطلبات عروض الأسعار العامة إن كانت موجودة.
- الصفحات العامة والمحتوى المعلوماتي عند الحاجة.

### البحث الإداري

يبقى منفصلًا داخل مركز القيادة، ويمكنه البحث بالمعرفات الدقيقة والسجلات الخاصة حسب الصلاحية، مع Masking وتسجيل استخدام البحث الحساس.

### قدرات البحث

- تطابق دقيق للعناوين والمعرفات.
- Full Text Search للأسماء والعناوين والوصف والوسوم المسموحة.
- Prefix search للاقتراحات.
- Fuzzy matching للأخطاء البسيطة بعد اختبار `pg_trgm` أو التقنية القائمة.
- تطبيع عربي منضبط للبحث فقط، مثل المسافات والتشكيل وبعض أشكال الهمزة، من دون تغيير النص الأصلي.
- تطبيع إنجليزي للحالة والمسافات.
- Synonyms معتمدة حسب التصنيف والسوق.
- Filters للدولة والمدينة والتصنيف والنوع والسعر والتاريخ والحالة المناسبة.
- Sorting واضح: صلة، أحدث، سعر، موقع عند توفره، ولا تستخدم شارة التوثيق كعامل ترتيب.
- Cursor pagination.
- Autocomplete لا يكشف محتوى خاصًا أو كلمات قليلة الاستخدام تخص شخصًا واحدًا.

### قواعد الصلة والترتيب

وثق Ranking weights ولا تجعلها صندوقًا أسود. ترتيب عضوي مقترح:

- التطابق الدقيق.
- العنوان.
- التصنيف والوسوم.
- الوصف.
- الحداثة.
- جودة اكتمال الإعلان ضمن معايير معلنة.
- الموقع عندما يختاره المستخدم.

الإعلان المدفوع لا يختلط بالنتيجة العضوية؛ يظهر في Placement معلن بوضوح. التوثيق لا يعطي Boost.

### الأمان والأداء

- RLS وحالة النشر والسوق تطبق قبل النتيجة.
- Search index لا يحتوي هاتفًا خاصًا أو مستندًا أو رسالة.
- إذا استخدمت Search document مشتقًا، احفظ `source_type/source_id/version` وحدثه Idempotently.
- GIN للـFull Text وIndexes ملائمة للفلاتر بعد `EXPLAIN`.
- لا تضف Partitioning بلا حاجة مثبتة.
- إذا تجاوز Postgres حدود الأداء المثبتة لاحقًا، استخدم Search adapter يسمح بمحرك خارجي من دون تغيير واجهة المنتج أو مصدر الصلاحيات؛ لا تنفذ محركًا خارجيًا الآن بلا حاجة.

## 11. تحليلات البحث

أضف داخل تحليلات مدير المنصة:

- عدد عمليات البحث.
- الجلسات التي استخدمت البحث.
- أكثر الاستعلامات بعد التطبيع.
- الاستعلامات بلا نتائج.
- الاستعلامات ذات نتائج بلا نقرة.
- زمن أول نقرة.
- التصنيفات والفلاتر الأكثر استخدامًا.
- أكثر اقتراحات Autocomplete اختيارًا.
- Funnel: بحث → نتيجة → فتح → تواصل/مفضلة/سلة/طلب.
- أداء البحث حسب الدولة والمقاس.
- Latency وError rate للبحث.
- Search index freshness.

قواعد الخصوصية:

- لا تسجل كلمات المرور أو أرقام الجوال أو البريد أو النصوص الطويلة كاستعلام.
- نظف الاستعلام وحد الطول وارفض الأنماط الحساسة.
- الاستعلامات النادرة لا تظهر في تقارير أصحاب الحسابات.
- صاحب الإعلان يرى الكلمات/التصنيفات التي أوصلت إلى إعلانه بصورة مجمعة فقط وبعد حد أدنى للخصوصية، ولا يرى سجل زائر فردي.
- أضف قائمة استبعاد لعبارات حساسة وRetention أقصر للأحداث الخام.

أضف صندوق عمل لـ«فجوات المحتوى»: عمليات بحث متكررة بلا نتائج، مع اقتراح إنشاء تصنيف أو محتوى أو تحسين Synonym، ولا تنشئ شيئًا تلقائيًا.

## 12. ضبط تكلفة التحليلات والبيانات

أنشئ **Analytics Cost & Volume Governance**.

اعرض:

- الأحداث بالساعة واليوم والشهر.
- الحجم التخزيني الخام والمجمع.
- أكثر أنواع الأحداث استهلاكًا.
- نسبة الأحداث غير المستخدمة في تقرير أو تنبيه.
- حجم كل Index وتكلفة الاستعلامات الثقيلة.
- نمو قاعدة البيانات وStorage.
- Retention الحالية والبيانات المتوقع حذفها/تجميعها.
- حدود الخطة الفعلية إن أمكن قراءتها بأمان، من دون ادعاء تكلفة غير مؤكدة.

قواعد التحكم:

- لا تجمع حدثًا ليس له غرض موثق أو تقرير أو Guardrail.
- Batch insert وDeduplication.
- Rollups ساعية/يومية Incremental.
- Sampling مسموح فقط للأحداث منخفضة القيمة وعند توثيق النسبة.
- لا تعمل Sampling لأحداث الأمان أو الطلبات أو الفواتير أو المدفوعات أو القرارات الإدارية.
- Retention مختلفة للخام والمجمع.
- حذف زمني آمن واختبار قبل التشغيل.
- تنبيه عند تجاوز نسبة من الميزانية أو نمو غير طبيعي.
- Kill switch للأحداث منخفضة الأولوية، مع بقاء الأحداث الحرجة.
- لا تستخدم Dashboard تعتمد على Scan كامل للأحداث الخام.

## 13. التحليلات اللحظية

أضف **Realtime/Recent Activity** بصورة مدروسة:

- النشاط خلال آخر 5 و15 و60 دقيقة.
- الصفحات النشطة الآن بصورة تقديرية.
- البحث الحالي بصورة مجمعة.
- الحملات التي تستقبل ظهورًا ونقرًا الآن.
- فشل Event ingestion أو ارتفاعه.
- آخر أحداث تشغيلية حساسة في مركز القيادة.

قواعد:

- اكتب بوضوح أنها أرقام حديثة/تقديرية وقد تتأخر.
- لا تعرض هوية زائر أو مساره الفردي لصاحب المتجر.
- استخدم Rolling aggregates أو Realtime آمن، لا بث جدول الأحداث الخام.
- Throttle للتحديث ولا تنفذ Query لكل ثانية لكل مستخدم.
- إذا تعطل Realtime، ارجع لآخر Aggregate مع وقت التحديث.
- الطلبات والفواتير والمدفوعات النهائية تأتي من مصدرها الحقيقي، لا من Event لحظي تقريبي.

## 14. إطار اختبارات A/B

أنشئ **Experimentation Framework** مرتبطًا بنسخ المحتوى والتحليلات، لا تعديلات عشوائية في الصفحة المنشورة.

### مكونات التجربة

- اسم وفرضية واضحة.
- المالك والمراجع.
- الصفحة/المكون/Placement المستهدف.
- Control وVariants مبنية على نسخ منشورة صالحة.
- الجمهور والاستبعادات.
- نسبة التوزيع.
- Primary metric واحد محدد مسبقًا.
- Guardrail metrics.
- الحد الأدنى للمدة والعينة.
- تاريخ البدء والانتهاء.
- حالات Draft/Review/Scheduled/Running/Paused/Completed/Invalid/Archived.

### قواعد النزاهة

- Assignment ثابتة للمستخدم/الجلسة خلال التجربة باستخدام مفتاح آمن، ولا تتغير مع كل Refresh.
- لا يختار العميل Variant بنفسه.
- افحص Sample Ratio Mismatch وتسرب الجمهور.
- لا تعلن فائزًا تلقائيًا مبكرًا.
- لا تغير Primary metric بعد بدء التجربة بلا إبطال النسخة السابقة.
- سجل كل تعديل.
- أوقف التجربة عند تدهور Guardrail أو الأداء أو الأمان.
- لا تجرب على تسجيل الدخول، الموافقات القانونية، الخصوصية، إجمالي الدفع أو عناصر سلامة المستخدم بلا مراجعة مستقلة.
- لا تستخدم التوثيق لتقسيم يمنح مزايا وظيفية.

النتائج تعرض Effect size وConfidence/uncertainty ومدة التجربة والعينة والجودة، ولا تكتفي بلون أخضر أو كلمة «فائز».
