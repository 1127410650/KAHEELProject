# الإغلاق الكامل لنسخة مدير النظام الحديثة

الطلب ضخم (39 قسمًا) ويحتوي أنظمة جديدة لم تُبنَ بعد. تنفيذه دفعة واحدة يعني كتابة آلاف الأسطر
دون اختبار فعلي بينها، وهذا يخالف شرط «لا زر صامت». لذلك أقسّمه إلى 4 دفعات متسلسلة داخل هذه
المرحلة نفسها، وكل دفعة تُختبر فعليًا قبل الانتقال، والتقرير النهائي يُكتب بعد الدفعة الرابعة.

## الوضع الحالي (جرد فعلي)

موجود ومنفّذ داخل `/admin`: الرئيسية، المستخدمون + ملف المستخدم، المنشآت + ملف المنشأة،
الإعلانات + ملف الإعلان، البلاغات (`reports` + `listing-reports`)، سجل العمليات،
التوثيق + ملف الطلب، الأنشطة، الأدوار، سجل التدقيق، الإعدادات، المناطق والمدن.
الصدفة `AdminShell` والمكونات `AdminDetail` / `AdminEnforcement` / `AdminNotes` / `AdminEntityLink`.

غير موجود ويحتاج بناء: البحث الإداري الموحد، قائمة العمل والإسناد (Claim/Transfer)،
«سلامة المعلن»، إعادة النشر بمدة، الإعلان بالنيابة، Tokens الألوان الإدارية،
وتوحيد نظام الحظر والتقييد في نموذج واحد للمستخدم والمنشأة.

## الدفعة 1 — الأساس المشترك (قاعدة البيانات + الهوية + الألوان)

- Migration واحد: جدول الإسناد `mkt_admin_assignments` (طلب مشترك + Claim + تحويل + قفل
  يمنع قرارين متعارضين)، جدول/دالة القيود الموحدة للمستخدم والمنشأة، دالة `mkt_advertiser_safety`،
  دالة `mkt_admin_search` موحدة، دالة `mkt_listing_republish` بمدة، ودوال الإعلان بالنيابة.
  كلها `SECURITY DEFINER` + `search_path` ثابت + `EXECUTE` لـ `authenticated` فقط + تحقق
  خادمي من `system_owner`/الصلاحية الجزئية + كتابة في `audit_log`.
- توسيع `mkt_admin_overview` بالعدادات الناقصة: المحظورون، غير المسندة، المسندة لي، الإجراءات العاجلة.
- Tokens ألوان الإدارة في `src/styles.css` (`--admin-critical/urgent/pending/progress/done/idle/verify`)
  ومكوّن `AdminStatusBadge` موحّد (لون + نص + أيقونة + أولوية) لا يعتمد اللون وحده، ولا يمسّ السوق.
- تثبيت هوية الإدارة في `AdminShell`: عزل حساب الأدمن عن إحصائيات المنشآت/المعلنين، ومنع أي
  Bottom Nav/Footer للسوق، وزر «معاينة السوق» بنفس التبويب مع «العودة إلى الإدارة».

## الدفعة 2 — البحث الموحد والرئيسية والعدادات

- شريط بحث إداري في رأس `AdminShell` + صفحة `/admin/search` تعرض النتائج مجمعة حسب النوع
  (مستخدمون، منشآت، إعلانات، بلاغات، توثيق، أنشطة) مع عدد لكل نوع، حد نتائج، تطبيع الأرقام
  العربية/الغربية، بحث جزئي، وإخفاء الحقول الحساسة بحسب الصلاحية.
- إكمال بطاقات الرئيسية الـ12 وقسم «يحتاج إجراء» بجميع الصفوف، كل بطاقة تقرأ من نفس مصدر القائمة
  وتمرر الفلتر الصحيح في نفس التبويب.
- توحيد أسماء الحالات (`pending` / `pending_review` / `under_review`) في طبقة واحدة،
  ومعالجة الفلتر المحفوظ القديم حتى لا يخفي سجلات صحيحة.

## الدفعة 3 — الصفحات والإجراءات

- المستخدمون والمنشآت: بحث وفلاتر وفرز وترقيم حقيقي وعداد نتائج، والصف كله قابل للفتح.
- الملفات التفصيلية: إكمال التبويبات الناقصة، وبطاقة «سلامة المعلن»، والإجراءات الإدارية
  (تقييد/إيقاف/حظر/رفع/إبطال الجلسات/إشعار/ملاحظة/إسناد) بسبب إلزامي ومدة وتأكيد وقفل
  ضد الضغط المتكرر، مع منع حظر آخر `system_owner` أو منح صلاحية أعلى.
- الإعلانات: تحويل القائمة إلى شبكة بطاقات شبه مربعة (عمود واحد/عمودان على الجوال، شبكة على
  الكمبيوتر) بكل الحقول المطلوبة والإجراءات السريعة، مع تبويبات وفلاتر وفرز كاملة،
  والفلتر الافتراضي «الكل» عند الدخول المباشر.
- التوثيق: إصلاح «اعتماد» ليكون خادميًا فعليًا مع تحديث حالة الحساب/المنشأة وإشعار وسجل،
  ومستندات بـ Signed URLs قصيرة غير مخزنة مع تسجيل كل فتح.
- إعادة النشر بمدة (1/3/7/14/30) بنفس الرابط والصور والإحصاءات.
- الإعلان بالنيابة: بحث عن الجهة، إنشاء باسمها، وتسجيل المنشئ الإداري.
- البلاغات: إكمال الفلاتر والإجراءات وربط كل إجراء بسجلات البلاغ والإعلان والمستخدم والمنشأة والتدقيق.
- الملاحظات الداخلية والتنبيهات الإدارية موحّدة على الأنواع الخمسة.

## الدفعة 4 — الاختبار والإغلاق

- Button Audit وNavigation Audit فعليان (لا `_blank`، لا `window.open`، حفظ البحث/الفلاتر/التمرير).
- Playwright: حساب مدير النظام (35 سيناريو)، مستخدم عادي، مشرف محدود، اختبارات أمنية
  (تزوير role/user_id/tenant_id، RPC مباشرة، تعديل سجل التدقيق، Signed URL لمستخدم آخر،
  اعتماد مزدوج، قراران متعارضان، Cache بعد الخروج).
- المقاسات 320/390/768/1024/1280/1366/1440 داخل الإدارة + Regression للسوق على 390 و1366.
- `tsgo --noEmit` و`vite build`، Console = 0، Overflow = 0.
- تنظيف بيانات QA (رفع القيود والحظر، حذف ناعم لإعلانات QA، ملفات يتيمة) مع الحفاظ على سجل التدقيق.
- التقرير `.lovable/audit/2026-08-04-admin-complete-final-closure.md` مع اللقطات المطلوبة.

## ملاحظات صريحة

- الموقع (القسم 20) يمسّ نموذج الإعلان في السوق وليس الإدارة فقط؛ سأفحصه وأصلح ما هو مكسور
  فعليًا دون إعادة تصميم مكوّن الموقع.
- قيود مثل «منع التقييم» و«منع التعليقات» لن تُعرض لأن الميزتين غير موجودتين، حسب شرط
  «لا تعرض قيدًا غير منفذ وظيفيًا».
- لا نشر، ولا مراحل أخرى، ولا عودة لأي جزء من النظام القديم.

## تفاصيل تقنية

Migration واحد لكل دفعة عند الحاجة، مع `GRANT` لكل جدول جديد وسياسات RLS مقيّدة بدور المنصة.
لا لمس للجداول القديمة إلا لإضافة أعمدة لازمة. كل RPC إداري يتحقق من الصلاحية داخليًا ولا يعتمد
على أي تحقق في العميل. العميل يستخدم `mkt-platform.ts` كطبقة وحيدة للنداءات الإدارية.
